Installation

How to set up shadcn-aurelia in an Aurelia 2 project.

Requirements

  • Aurelia 2 (RC or later) with TypeScript.
  • Vite 7 with @aurelia/vite-plugin. Vite 8 currently breaks Aurelia's TC39 decorators (its Oxc transform strips types but leaves decorators raw) — stay on Vite 7 until that is resolved.
  • Tailwind CSS v4 via @tailwindcss/vite, with @import "tailwindcss" in your stylesheet.
  • A @ path alias pointing at src/ (in both tsconfig.json and Vite).

Option 1 — start from the template

The CLI ships a pre-configured starter (the source lives at templates/aurelia-vite): Aurelia 2 + Vite 7 + Tailwind v4 + the @ alias, ready for init. 

npx shadcn-aurelia@latest create my-app
cd my-app
npm install
npx shadcn-aurelia init
npm run dev

Option 2 — add to an existing app

1. Tailwind CSS v4

If you don't have Tailwind yet:

npm install tailwindcss @tailwindcss/vite

Add the plugin to vite.config.ts and create a stylesheet imported from main.ts:

// vite.config.ts
import { defineConfig } from 'vite'
import aurelia from '@aurelia/vite-plugin'
import tailwindcss from '@tailwindcss/vite'
import { fileURLToPath } from 'node:url'

export default defineConfig({
  plugins: [aurelia({ useDev: true }), tailwindcss()],
  resolve: {
    alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) },
  },
})
/* src/styles/globals.css */
@import "tailwindcss";

2. Path alias

// tsconfig.json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": { "@/*": ["src/*"] }
  }
}

3. Run init

npx shadcn-aurelia init

init verifies the prerequisites above, writes a components.json, downloads the theme stylesheet (CSS variables + base layer + animations) as shadcn-aurelia.css next to your Tailwind entry stylesheet, and imports it there.

4. Add components

npx shadcn-aurelia add button
npx shadcn-aurelia add dialog form data-table-adapter

Files land under your configured aliases (@/components/ui/button/… by default), with npm dependencies (like @shadcn-aurelia/primitives) installed automatically. Then import and use: 

<import from="@/components/ui/button"></import>

<ui-button variant="outline">Click me</ui-button>

Webpack

The components themselves are bundler-agnostic TypeScript + Aurelia conventions, and work under Webpack with @aurelia/webpack-loader. You will need Tailwind v4 via PostCSS (@tailwindcss/postcss) and a @ alias in your Webpack config. The CLI's preflight currently checks for Vite; use --force-free manual setup by copying components.json and the theme CSS from a Vite project, or run the CLI in a sibling Vite app and copy the output. First-class Webpack preflights are planned.

Monorepos

The CLI operates on one app package at a time: it looks for package.json and components.json directly in its working directory (it does not search parent directories). Run it from the app package, or pass --cwd when invoking from the workspace root. Given a pnpm workspace like this: 

acme/
├── pnpm-workspace.yaml
├── pnpm-lock.yaml            # root lockfile
├── apps/
│   ├── web/                  # Aurelia app
│   │   ├── package.json
│   │   ├── tsconfig.json     # "@/*" → "src/*"
│   │   └── src/
│   └── admin/                # another Aurelia app
└── packages/
    └── shared/

each app gets its own components.json and component copies:

# from the workspace root
npx shadcn-aurelia init --cwd apps/web
npx shadcn-aurelia add button dialog --cwd apps/web
npx shadcn-aurelia diff --cwd apps/web

# or equivalently, from inside the app package
cd apps/web
npx shadcn-aurelia add button dialog

Package manager detection walks up parent directories until it finds a lockfile or workspace marker (pnpm-lock.yaml/pnpm-workspace.yaml, yarn.lock, bun.lock, package-lock.json). add then runs pnpm add/yarn add/bun add inside the app package, which those workspace-aware managers resolve against the root lockfile — npm dependencies such as @shadcn-aurelia/primitives land in the right package.json.

npm workspaces are handled too: npm itself does not detect a workspace root when run inside a sub-package (a plain npm add there would create a nested lockfile), so when the root lockfile belongs to an npm workspace the CLI installs from the workspace root instead — npm install <deps> -w apps/web.

Shared UI package

Components are copied per app by default; the copies are yours and may diverge — that is the point of the copy-paste model. To share one set of components across apps instead, map a workspace alias to the shared package in the app's tsconfig.json and Vite config, and point the aliases in components.json at it. add resolves every alias through the tsconfig paths (longest prefix wins), so the files land in the shared package while imports are rewritten to the alias: 

// apps/web/tsconfig.json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"],
      "@acme/ui/*": ["../../packages/ui/src/*"]
    }
  }
}
// apps/web/vite.config.ts → resolve.alias
{
  '@': fileURLToPath(new URL('./src', import.meta.url)),
  '@acme/ui': fileURLToPath(new URL('../../packages/ui/src', import.meta.url)),
}
// apps/web/components.json
"aliases": {
  "components": "@acme/ui/components",
  "ui": "@acme/ui/components/ui",
  "lib": "@acme/ui/lib"
}
$ npx shadcn-aurelia add button login-01 --cwd apps/web
  + ../../packages/ui/src/lib/cn.ts
  + ../../packages/ui/src/components/ui/button/button.ts
  + ../../packages/ui/src/components/blocks/login-01/login-01.ts
  …

Imports inside the copied files use the alias (import { cn } from '@acme/ui/lib/cn'), so every app that consumes the shared package needs the same tsconfig paths and Vite alias. diff compares against the shared location the same way. One caveat: npm dependencies (@shadcn-aurelia/primitives, clsx, …) are installed into the app you ran the CLI from — under pnpm's strict layout, declare them in the shared package's package.json as well so its files can resolve them.
