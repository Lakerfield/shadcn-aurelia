Accessibility

What we test, what we guarantee, and the keyboard map per component.

Statement

  • axe is merge-blocking. Every documentation page — and therefore every shipped example of every component — must pass axe-core with zero violations before it lands.
  • Keyboard behavior follows the WAI-ARIA APG. Interactive components implement the patterns from the ARIA Authoring Practices Guide, matching the Radix behavior shadcn/ui users expect. The maps below are verified per component.
  • ARIA wiring is engine-owned. Roles, states (aria-expanded, aria-selected, …) and relationships (aria-labelledby, aria-describedby, aria-controls) are maintained by the behavior engines, so they stay correct across every state transition.
  • Forms wire themselves. The field component connects label, description and error message to the control and toggles aria-invalid from validation state.
  • Light DOM. No shadow roots — assistive technology sees one coherent document, and your own a11y tooling can inspect everything.
  • Found an issue? Accessibility bugs are prioritized — open an issue.
